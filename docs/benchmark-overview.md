# LLM Benchmark 平台讲解文档

## 一、这个平台是干什么的

**一句话：让模型互相出题、互相答题、互相评判，最终用 Elo 积分排出高下。**

传统的 LLM 评测方式是准备一批固定题目，让模型去答，再由人工或固定标准打分。这种方式有两个问题：

1. 题目固定，模型厂商可以专门针对测试集优化（"刷题"）
2. 人工打分成本高，标准主观

这个平台的核心思路是**对抗式评测**：不准备固定题目，而是让模型 A 来出题刁难模型 B，再由第三方模型来判断谁赢了。这样题目是动态生成的，无法提前准备，评判也是自动的。

## 三、核心评测流程（最重要）

### Phase 1：初始化
用户在界面上：
1. 注册参赛模型（填模型名 + API地址）
2. 选择评测维度（知识 / 推理 / 代码 / 安全）
3. 设定对战轮数（比如 5 轮）

### Phase 2：对抗对战（系统自动执行）

每一轮对战分 4 步：

```
Step 1  模型 A（攻击者）→ 根据维度生成一道刁钻题目
            ↓
Step 2  模型 B（防守者）→ 回答这道题
            ↓
Step 3  裁判模型 → 判断 B 的回答是否正确
            ↓
Step 4  更新 Elo 积分，记录胜负，角色互换
```

然后 B 变成攻击者，出题刁难 A，再走一遍上面的流程。

### Phase 3：多轮迭代

系统会记录每个模型的弱点（哪类题容易答错），下一轮攻击时**针对对手的弱点出题**，让评测越来越精准。

### Phase 4：生成报告

- Elo 排行榜（整体 + 按维度分开）
- 每个模型的弱点诊断
- 胜率分析

## 四、Elo 积分是什么

借鉴自国际象棋的评分系统，简单说：

- 打败强对手 → 加很多分
- 打败弱对手 → 加少量分
- 输给强对手 → 扣少量分
- 输给弱对手 → 扣很多分

公式：
```
新积分 = 旧积分 + 32 × (实际结果 - 预期胜率)

预期胜率 = 1 / (1 + 10^((对手积分 - 自己积分) / 400))

实际结果：赢 = 1，输 = 0，平 = 0.5
```

初始积分：所有模型从 **1500 分**开始。

## 五、四个评测维度

| 维度 | 攻击策略 | 典型题目示例 |
|------|---------|------------|
| 知识型 | 冷僻知识、边界知识、易混淆概念 | "请区分贝叶斯概率和频率主义概率的本质差异" |
| 推理型 | 多步推理陷阱、逻辑循环、反直觉数学 | "一个房间有3盏灯，开关在门外，只能进一次，如何判断哪个开关控制哪盏灯" |
| 代码型 | 边界条件、隐藏bug、复杂依赖 | "这段代码在输入为空列表时会抛出什么异常" |
| 安全型 | 伦理边界、有害请求变体、社会工程 | 测试模型是否会拒绝不当请求 |

## 六、数据库结构（7张表）

```
models          → 注册的模型信息
evaluation_tasks → 评测任务（一个任务包含多轮对战）
questions       → 每轮生成的题目
battles         → 每场对战的详细记录（题目、双方回答、胜负）
elo_ratings     → 各模型在各维度的 Elo 积分
weakness_analysis → 各模型的弱点分析
reports         → 生成的评测报告
```

## 八、向技术部门讲解要点

### 讲解顺序建议

1. **先讲痛点**：现有评测为什么不够（固定题集、人工打分）
2. **再讲方案**：对抗式 = 动态出题 + 自动判断
3. **演示流程**：打开界面，注册两个模型，走一遍完整对战
4. **讲 Elo**：用国际象棋类比，大家都能理解
5. **讲可扩展性**：加新模型只需注册，加新维度只需加 prompt

### 预期会被问到的问题

**Q：裁判本身有偏见怎么办？**
A：目前裁判是攻击方自己（有利于攻击方），后续可配置独立第三方裁判模型，或多个裁判投票取多数。

**Q：Elo 积分受初始对战顺序影响大吗？**
A：有影响，但多轮迭代后会收敛。轮数越多结果越稳定，建议至少 10 轮以上。

**Q：安全维度的测试题会不会本身就不合规？**
A：题目由攻击模型生成，有边界——prompt 设计为测试"拒绝能力"，而不是直接生成有害内容。但这是需要持续监控的风险点。

**Q：支持多少个模型同时评测？**
A：当前是串行执行（一场对战结束再开下一场），多模型时轮数会指数级增长。生产环境需要改为并行调度。

## 九、当前已知的局限和后续方向

### 已知局限

| 问题 | 影响 | 解决方向 |
|------|------|---------|
| 串行执行 | 多模型评测慢 | 引入并发任务队列（Celery / APScheduler） |
| 裁判是攻击方自己 | 可能偏向攻击者 | 配置独立第三方裁判 |
| 弱点分析未自动化 | weakness_analysis 表目前为空 | 对战结束后自动统计失败模式写入 |
| SQLite 并发限制 | 多用户同时操作可能冲突 | 生产环境切换 PostgreSQL |
| 无鉴权 | 任何人都能访问 | 加 API Key 或 OAuth |

### 后续迭代方向

- [ ] 多 GPU 并行评测
- [ ] 更丰富的可视化（积分变化曲线、胜率热力图）
- [ ] 支持自定义评测维度（用户上传 prompt 模板）
- [ ] 历史趋势追踪（同一模型不同版本的横向比较）
- [ ] 导出报告为 PDF

## 十、快速启动

```bash
# 1. 启动后端（数据库自动初始化）
cd backend
py -3.11 -m uvicorn app.main:app --host 0.0.0.0 --port 8080

# 2. 启动前端
cd frontend
npm run dev

# 3. 使用 CLI
benchmark status                          # 查看系统状态
benchmark model register gpt4 gpt-4      # 注册模型
benchmark task create test-battle \
  --dimension knowledge --models 1,2 --rounds 5
benchmark task start 1                   # 开始评测
```

**访问地址：**
- Web 界面：http://localhost:5173
- API 文档：http://localhost:8080/docs

## 十一、配置文件说明

